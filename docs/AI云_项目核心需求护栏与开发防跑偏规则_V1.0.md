# AI云 · 项目核心需求护栏与开发防跑偏规则 V1.0

> 文件建议放置位置：项目根目录 `AGENTS.md` 或 `.cursor/rules/aiyun-core.mdc`  
> 适用对象：Codex、Cursor、人工开发者  
> 优先级：高于普通页面需求、临时灵感、功能扩展建议。

---

# 0. 一句话总原则

> AI云不是“通用 AI 平台”，不是“聊天机器人后台”，不是“全渠道客服中心”。  
> AI云是：**帮助工业设备制造企业把官网升级为 AI 接待、产品咨询、询盘留资和线索跟进工具的工业官网获客系统。**

任何功能只有在能直接增强以下闭环时，才允许进入 P0 / P1：

```text
工业企业官网访客
→ AI 根据企业产品资料回答
→ 识别选型 / 报价 / 图纸 / 定制 / 交期等高意向需求
→ 自动留资
→ 销售查看会话和线索
→ 销售跟进
→ 根据未解决问题补充资料
```

# 1. 项目定位不可变更

## 1.1 核心客户

第一阶段只服务：

```text
工业设备制造企业
```

优先行业：

```text
工业机柜 / 控制柜
工业冷水机 / 温控设备
自动化设备
激光设备
包装设备
检测 / 测量设备
外贸机械企业
```

## 1.2 客户购买的不是技术名词

禁止把产品描述成：

```text
RAG 平台
Agent 平台
多模型平台
向量数据库产品
通用企业 AI 平台
```

客户可理解的价值必须是：

```text
官网 24 小时接待客户
产品资料变成可回答的销售资料
报价 / 定制 / 图纸需求自动留资
销售优先跟进高意向客户
知道客户最常问什么、官网缺什么内容
```

## 1.3 产品名称与对外表达

主产品名称：

```text
AI云 · 工业官网获客系统
```

一句话表达：

```text
让工业官网同时具备“AI 接待、产品咨询、询盘留资、线索跟进”能力。
```

# 2. 功能准入规则

所有新功能在开发前必须回答 5 个问题。

任何一个问题回答为“否”或“不确定”，不得直接开发，必须进入 `BACKLOG.md` 等待产品确认。

```text
Q1：它是否直接服务“官网咨询 → 留资 → 跟进”的闭环？
Q2：它是否是工业设备企业的高频真实需求？
Q3：它是否能在 1 个工作区、1 个机器人、1 个官网 Widget 场景中验证？
Q4：它是否不会增加复杂 CRM、ERP、工作流、计费或多渠道依赖？
Q5：它是否能在 3–7 天交付模板中复用？
```

## 2.1 功能分级

### P0：必须做

```text
1. 企业工作区与数据隔离
2. 企业管理员 / 成员登录
3. 产品资料上传、解析、索引、可用状态
4. 知识库问答与来源引用
5. 官网 Widget
6. 公共聊天接口（SSE 或等价流式方式）
7. 域名白名单与 Site Key
8. 选型 / 报价 / 图纸 / 定制 / 交期触发留资
9. 会话记录
10. 线索列表、线索详情、跟进状态
11. 未解决问题统计
12. 基础 Dashboard
```

### P1：在 P0 跑通后做

```text
1. 多语言
2. 图纸 / 附件上传
3. 线索导出
4. 产品资料模板
5. FAQ 批量生成
6. 高级数据分析
7. 网站诊断与内容建议
8. JSON-LD / Schema 输出
9. 月度获客报告
10. 角色与成员邀请增强
```

### P2：暂不做

```text
CRM 全功能
ERP / MES / OA 深度对接
工作流编排
Agent 市场
模型市场
支付订阅
复杂多租户计费
企微 / 钉钉 / 飞书全渠道深度接入
电话呼叫中心
实时 GEO 排名承诺
自建大模型训练平台
```

# 3. 开发前必须执行的“需求闸门”

每个任务必须先创建一个任务说明，格式固定如下：

```md
# Task ID: P0-XXX

## 用户价值
这个功能帮工业企业客户解决什么具体问题？

## 对核心闭环的影响
它增强：
- [ ] 官网接待
- [ ] 产品问答
- [ ] 选型追问
- [ ] 留资
- [ ] 销售跟进
- [ ] 内容优化

## 用户故事
作为【谁】，我希望【做什么】，从而【获得什么结果】。

## 不做什么
明确列出本任务禁止扩展的能力。

## 允许修改目录
明确到目录级别。

## 禁止修改目录
明确到目录级别。

## 接口影响
新增 / 修改哪些 API。

## 数据库影响
是否需要 migration。若不需要，明确写“无”。

## 验收标准
只写可验证的结果，至少 3 条。
```

没有 Task ID、没有“不做什么”、没有验收标准的任务，禁止开始编码。

# 4. AI 开发者强制执行规则

以下规则同时适用于 Codex、Cursor。

## 4.1 开始编码前

必须先输出：

```text
1. 对任务的理解
2. 与 AI云核心闭环的关系
3. 当前仓库中相关模块的位置
4. 计划修改的文件清单
5. 不会修改的文件清单
6. 风险和待确认问题
```

如果任务与核心闭环无关，必须明确提示：

```text
“该需求不属于当前 P0 / P1 范围，建议放入 Backlog，等待产品确认。”
```

不得自行扩展实现。

## 4.2 编码过程中

必须遵守：

```text
1. 一次只实现一个 Task ID。
2. 不同时改 UI、数据库、接口、部署四个大模块，除非任务明确要求。
3. 不重构无关模块。
4. 不替换技术栈。
5. 不新增大型依赖，除非在任务中明确批准。
6. 不修改环境变量名称、数据库 schema、认证逻辑，除非任务明确要求。
7. 不删除已有功能，除非任务明确写明“替换 / 废弃”。
8. 不为了“更完整”追加 P2 功能。
9. 不为了“更好看”改动全局设计系统。
10. 不在没有真实资料时编造工业参数、认证、交期、报价或案例。
```

## 4.3 完成后

必须输出：

```text
1. 已完成的功能
2. 修改文件清单
3. 未修改但相关的文件
4. 接口变化
5. 数据库 migration
6. 测试命令和结果
7. 已知限制
8. 下一步建议（只能建议 1 个紧邻任务）
```

不得输出“顺便做了以下功能”。

# 5. Codex 与 Cursor 分工边界

## 5.1 Codex 负责

```text
apps/api/**
apps/worker/**
infra/**
数据库 schema / migration
认证、权限、工作区隔离
RAG、文档解析、索引、队列、SSE
API 测试、集成测试、安全检查
```

## 5.2 Cursor 负责

```text
apps/console/**
apps/widget/**
packages/ui/**
页面布局、组件、交互状态、表格、表单
响应式样式
Mock 数据与 API 接入层
```

## 5.3 绝对禁止同时修改

```text
同一个文件
同一个 API route
同一个 migration
同一个 Widget 入口
同一个共享类型定义
```

协作顺序：

```text
Codex 先定义 API 契约
→ 输出 request / response 示例
→ Cursor 用 Mock 接口完成 UI
→ Cursor 接真实接口
→ Codex 做集成验证
```

# 6. 页面开发防跑偏规则

所有页面必须属于以下信息架构，禁止自行新增“平台型页面”。

```text
登录 / 邀请激活
Dashboard
知识库
机器人配置
会话中心
线索管理
数据分析
网站诊断
设置中心
套餐展示
官网 Widget
```

## 6.1 页面开发顺序

```text
P0 页面：
登录
Dashboard
知识库
上传资料
机器人配置
对话测试
会话中心
线索列表
线索详情
网站接入 / Widget

P1 页面：
未解决问题
数据分析
网站诊断
团队成员
套餐升级
```

## 6.2 每个页面必须有

```text
加载状态
空状态
错误状态
权限不足状态
移动端基础适配
真实业务文案
```

## 6.3 页面禁止出现

```text
虚假的 AI 能力承诺
“保证排名第一”
“100% 准确”
“自动成交”
“无限制免费模型”
与工业官网获客无关的 Agent 市场、插件市场、工作流市场
```

# 7. RAG 与 AI 回答规则

AI 不能像通用聊天机器人一样自由回答。

必须遵守：

```text
1. 优先基于当前工作区知识库回答。
2. 回答应尽可能展示资料来源。
3. 知识库没有内容时，明确说“暂未找到资料”，不得编造。
4. 报价、交期、非标、图纸、工艺、选型风险、认证要求必须触发人工确认或留资。
5. 工业参数不确定时必须使用：
   “以工程师确认、正式图纸和报价为准。”
6. 不跨工作区检索。
7. 不在日志中记录客户敏感资料全文。
```

## 7.1 高意向触发关键词

至少覆盖：

```text
报价
价格
多少钱
询价
图纸
CAD
PDF
定制
非标
样品
交期
采购
合同
下单
联系方式
电话
邮箱
项目
招标
参数确认
```

命中后行为：

```text
先完成当前问题的基础回答
→ 引导补充工况 / 型号 / 数量 / 图纸
→ 展示留资表单
→ 创建线索
→ 将会话摘要写入线索
```

# 8. 提交与合并规则

## 8.1 分支规则

```text
feature/p0-widget-ui
feature/p0-public-chat-api
feature/p0-lead-capture
feature/auth-invitation
fix/widget-domain-check
```

禁止：

```text
test
new
final
latest
fixall
aaa
```

## 8.2 每次提交必须小

单次 PR / 分支最好只对应：

```text
一个 Task ID
一个业务目标
一个可验收结果
```

## 8.3 合并前 Checklist

```text
[ ] 是否仍服务工业官网获客核心闭环？
[ ] 是否跨工作区隔离？
[ ] 是否有权限校验？
[ ] 是否有错误状态？
[ ] 是否影响 Widget？
[ ] 是否有测试？
[ ] 是否新增了未批准依赖？
[ ] 是否做了超出任务范围的内容？
[ ] 是否更新了任务状态？
```

任何一项为“否”或“不确定”，不合并。

# 9. 产品负责人决策规则

你是产品负责人，所有 AI 必须遵守：

```text
1. 不明确的需求先问，不猜。
2. 临时灵感不直接开发，先写入 Backlog。
3. 任何新功能先问：
   “它能否让客户更容易咨询、留资或跟进？”
4. 不能直接回答“能”，必须指出它对应核心闭环哪一环。
5. 如果功能只是“看起来很酷”，但不能改善咨询、留资、跟进、资料质量，默认不做。
```

# 12. 最终裁决规则

当出现“要不要做某功能”的争议时，使用以下公式：

```text
优先级 =
客户当前愿意付费程度
× 对官网询盘转化的直接影响
× 可模板化交付程度
÷ 开发复杂度
```

优先做：

```text
高付费 + 高转化影响 + 高复用 + 低复杂度
```

暂缓做：

```text
低付费 + 低转化影响 + 低复用 + 高复杂度
```

# 13. 这个项目当前唯一的胜利标准

不是“做了多少页面”，不是“接了多少模型”，不是“功能有多全”。

当前胜利标准只有：

```text
客户上传产品资料
→ 官网访客能问产品问题
→ AI 能回答或正确追问
→ 报价 / 图纸 / 定制需求被留资
→ 销售能在后台看到完整需求
→ 客户愿意为该闭环付费
```

只要功能不让这条链路更短、更稳、更容易卖，就不要开发。
